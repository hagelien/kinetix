# Kinetix Agent Guidelines

**Generated:** 2026-04-03 | **Commit:** b255fb0

## Overview

PK/PD calculator and forensic toxicology reference tool. React 18 SPA (Vite + TypeScript) with Vercel serverless API, Neon PostgreSQL, and a built-in wiki.

## Structure

```
kinetix/
├── src/                  # React SPA (primary frontend)
│   ├── components/       # React components (drug table, modeling/simulator, wiki editor)
│   ├── stores/           # Zustand stores (app, auth, drug, simulator)
│   ├── lib/              # Shared utilities (conversions, rangeUtils, storage)
│   ├── pages/            # Route pages (admin, login, wiki/*)
│   ├── workers/          # Web workers (kinetics computation via Comlink)
│   ├── data/             # Data loader — builds _searchKey at load time
│   └── types/            # TypeScript types (NumericRange, DrugComponent, etc.)
├── scripts/              # Operational and maintenance tooling (seeding, imports, migrations)
├── api/                  # Vercel serverless functions (see api/AGENTS.md)
│   ├── _lib/             # Shared API utilities (auth, db, response, schemas)
│   └── wiki/             # Wiki API routes
├── data/                 # Static drug + method data (TypeScript objects)
│   ├── components.ts     # ~1760 lines — all drug components (largest file)
│   └── methods.ts        # Analytical methods (CID arrays → component IDs)
├── db/                   # Drizzle ORM schema (PostgreSQL)
├── tools/enrichment/     # Data enrichment CLI (see tools/enrichment/AGENTS.md)
└── e2e/                  # Playwright E2E tests
```

The merge is a superset of the DELETE teardown in `api/drugs.ts`: it MOVES what a delete would drop rather than cascading it away. Metabolite/precursor edges (`drug_metabolites`, both `parent_drug_id` and `metabolite_drug_id`) repoint with self-edge + dedupe guards — this is the "links to the deleted page" the request names, DB-row side. The **content** side is `rewriteDrugLinksInJson`/`rewriteDrugLinksInHtml`, keyed on `href` (`/wiki/drug/<id>` and `/wiki/<monograph-slug>`), applied to `wiki_pages`/`wiki_revisions` content and `pending_edits.proposed_value` — mirrors `rewriteCitationIdsInJson` but for URLs. Loser's names become winner aliases (still searchable by the old spelling), popularity folds in, the loser's stub monograph is deleted (repointed instead if the winner somehow has none), then the loser drug row is deleted and `recomputeSummariesForDrug` refreshes the winner's cached aggregates. | Auth                  | `api/auth.ts`, `api/_lib/auth.ts`, `src/stores/authStore.ts`                            | JWT in httpOnly cookie                                                                                                  |
| Permissions (who may do what) | `src/lib/permissions.ts` (registry + pure `can()`), `api/_lib/permissions-store.ts` (`callerCan`, write path), `api/permissions.ts`, `src/lib/usePermissions.ts` (`useCan`), `src/components/admin/PermissionsAdminSection.tsx`, `drizzle/0089_permission_overrides.sql`, `docs/permissions.md` | The four-tier ladder in `roles.ts` says how privileged a user is; the **capability matrix** says what each tier may do, and admins adjust it at runtime from Admin → Permissions. Routes call `await callerCan(auth.role, CAP['…'])` instead of comparing `auth.role` to a literal, and components call `useCan('…')`, so a change moves the API and the UI together. `permission_overrides` stores only **deviations** from the shipped defaults (a stock install is empty and behaves exactly as before); `permission_override_history` is the audit log. Each capability carries a `floorTier` (the lowest tier an admin may select — every write/review capability floors at `authenticated` or above) and one minimum tier, which keeps the ladder monotone: no configuration can leave a higher tier holding less than a lower one. `admin.users.manage` and `admin.permissions.manage` are `locked` because both can grant privileges — an editor able to edit the matrix could grant themselves everything. An unknown capability id resolves to admin-only, and rows for ids a later release drops are ignored rather than migrated. `callerCan` skips the DB read when it cannot change the answer (admins hold everything; below-floor callers can never be granted), and the read goes through `getConfigDb()` — the same connection as `getDb()`, but a separate accessor so route unit tests, which queue mocked query results in handler order, aren't shifted by an infrastructure read. `methods.read`/`learn.read` are *either* the capability *or* the feature group (`rettstoks`, `kinetix-learn`), both defaulting to admin, i.e. today's behavior |
| Site settings (policy switches) | `src/lib/siteSettings.ts` (registry + `sanitizeSiteSettings`), `api/_lib/site-settings-store.ts` (`isReferenceGateEnabled`, cached read, write path), `api/admin.ts` (`?resource=settings`), `src/components/admin/SiteSettingsAdminSection.tsx`, `src/lib/siteSettingsApi.ts`, `drizzle/0096_site_settings.sql` | Runtime policy switches an admin flips from Admin → Settings. The capability matrix answers *who may do this*; these answer *is this rule in force at all*, for policies that are neither per-user nor per-tier. Structurally the matrix's twin: a compiled registry carries every switch and its shipped default, `site_settings` stores only **deviations** (a stock install is empty and behaves exactly as before, and setting a switch back to its default deletes the row rather than pinning it), ids a later release drops are ignored at read time, and the read goes through `getConfigDb()` + a 5 s per-instance cache because it sits on the write path. The **failure direction is the opposite of a feature flag's**: an unreadable table, a missing `DATABASE_URL`, a table predating the migration and a non-boolean `jsonb` value all resolve to the shipped default, and every switch here ships in its *stricter* position — a transient blip must never quietly drop a guard. First switch is `referenceGate.blockUnreviewedCitations`, which turns the read-in-full gate on and off. The check lives inside `assertReferencesJudgedForActor` — not at its four routes, so there is exactly one place the agent gate can be on or off, and deliberately **not** in the bare `assertReferencesJudged`, whose only direct caller is the `learning_unit` submission path. That path gates humans too and is a different guarantee (the reviewed source is the unit's substance, not an agent discipline), so it stays unconditional. Turned off, an agent's fact/parameter/entry citing an unreviewed resolvable source is accepted — the citation still joins the follow-up queues, it just no longer blocks. Making that promise true required widening `agent-sweep`'s `unreviewed_references` `used` CTE to include `parameter_entries` directly: for a **non-summarizable** parameter (`analyteStability`) `recomputeAndCacheParameterSummary` returns early and writes no `drug_parameter_revisions` row, so those sources reached neither arm of the queue. Survivable while the gate was unconditional (only a rejected pending review got you there); the ordinary path once it is switchable. The query is exported as `UNREVIEWED_REFERENCES_SQL` and the integration test executes THAT text, not a copy — same anti-drift rule as `CITATION_HAYSTACK`. Reporting a committed write is its own hazard, guarded at two levels: the PATCH route's post-commit matrix re-read is **best-effort** (`rows: null` on failure) rather than allowed to 500, since a client that reads an error as "the save did not happen" reverts its toggle and shows the gate as on while it is really off; and `applySiteSettings` **overlays the committed changes on its re-read** rather than returning `loadSiteSettings()` bare — that function answers a failed read with the shipped defaults, which is right for a gate check and exactly wrong for a write receipt |
| Parameter applicability (which gaps are real) | `src/lib/parameterApplicability.ts` (rules, `CORE_COVERAGE_PARAMETERS`, `ABSENT_RECHECK_DAYS`), `api/agent-sweep.ts` (`PARAMETER_GAPS_SQL`, `mode=parameter_gaps`), `api/drug-parameter-applicability.ts` + `api/_lib/parameterApplicabilityStore.ts`, `drugs.substance_class`, `drizzle/0097_parameter_applicability.sql`, `tests/integration/parameter-gap-queue.test.ts` | Answers *is this missing value actually work?* for the hourly maintenance agent. Its core-coverage queue was a bare "no row in `drug_parameters`" scan with no memory, so a pair that could never be filled sat at the head of the queue and was re-picked every cycle forever — the routine reported "benzoylecgonine bioavailability remains unset" on every run for weeks. Benzoylecgonine is a cocaine metabolite nobody administers, absolute bioavailability needs an administered dose, and belonging to a screening method sorted it ahead of everything else (`in_method` outranks popularity). Three layers now separate *unfillable* from *unfilled*, cheapest and broadest first: **substance class** — `drugs.substance_class` ∈ `drug`/`metabolite`/`endogenous`, and a spec's `requiresAdministration` (bioavailability and the five dose ranges) makes those parameters undefined for the non-`drug` classes. **`tmax` deliberately does not carry that flag**, though it reads like it should: a metabolite's time to peak is measured after the *parent* is dosed and is a routine published endpoint (cocaine studies report benzoylecgonine's), so the test is "needs a dose **of this substance**", not "describes absorption" — absolute bioavailability is a ratio against an IV reference dose of the same compound and the dose ranges *are* the dose, retiring several pairs per classification and covering new analytes for free; **explicit marker** — `drug_parameter_applicability`, an editor-gated per-pair row with a required `reason`, for one-offs the class rule cannot express; **absent cooldown** — a `verification_log` row with `concordance='absent'` suppresses the pair for `ABSENT_RECHECK_DAYS` only, because "no literature today" is a claim with a shelf life while the first two are claims about the quantity. Two directions matter. **Failing safe means staying visible**: an unrecognised `substance_class` normalizes to `drug` and the SQL filters with `= ANY(<non-administered list>)` rather than `<> 'drug'`, so a class a build has not heard of shows too many gaps rather than silently hiding real ones — a spurious gap costs one cycle, a hidden one hides missing data indefinitely. **Agents cannot retire their own work**: writing a marker needs `parameterApplicability.write`, whose `floorTier` is `editor` rather than the `contributor` its neighbours use — an admin must not be able to dissolve this boundary from the runtime matrix, because an agent that can declare a parameter undefined can hide a real gap as easily as an impossible one, permanently. A contributor agent that concludes a quantity cannot exist logs `absent` and says so in the parameter thread; the cooldown holds the pair until a human decides. **The classification is data, applied by code, never by a migration**: `data/substanceClasses.ts` is the one list; `scripts/seed-drugs.ts` applies it at insert (so a from-scratch database is classified) and `scripts/backfill-substance-classes.ts` applies it to a database that already holds the catalog, **after** the deploy. It was migration 0097's job and that was wrong twice over — a migration runs while the *previous*, unguarded build is still accepting writes, so an old writer can store a bioavailability moments after the conditional UPDATE's snapshot and the new API then serves a number for a pair its own queue calls impossible; and a migration runs once, which is the wrong shape for a list of scientific judgements that has already had four entries withdrawn after review, since a withdrawn entry stays wrong in every database that already ran it. **Deploying this needs one manual step**: after the new build is live, run `npm run backfill:substance-classes -- --apply` (dry-run without the flag). Skipping it is not a silent no-op with a small cost — it is the whole fix not shipping: on an existing database every analyte stays at the `drug` default and benzoylecgonine's bioavailability keeps heading the queue. It is deliberately not in `deploy-production.yml`, because a data mutation that runs automatically on production is a decision for whoever owns the deploy, not a side effect of this change. The script is idempotent, so running it again is free. It refuses a substance whose live data conflicts (naming the parameters), re-reads the class **inside** the per-drug lock so a reclassification committed mid-run is never overwritten, and **reports rather than reverts** a class the list no longer claims — from there an editor's deliberate correction and a withdrawn entry are indistinguishable, and the editor's must survive. Seeding likewise sets the class on insert only, never on conflict. **The bar for classifying a substance is "nobody administers it in any form", not "the body makes it" and not "it is a metabolite"** — morphine is a codeine metabolite and a marketed drug, GHB is endogenous and is sodium oxybate, beta-hydroxybutyrate is endogenous and is sold as ketone salts and esters with published human tmax, hydroxybupropion’s (+)-enantiomer was trialled as radafaxine, and cotinine has been given to humans in controlled dosing studies; all of them stay `drug`, and an investigational drug that never reached market still has a tmax somebody measured. Getting this wrong is not a spurious-gap-sized mistake in the other direction: it makes correct absorption and dose data unwritable and hides those gaps permanently. `endogenous` therefore ships with no members at all. Four wrong entries got into the metabolite list behind comments naming the *parent drug* — which answers "is it a metabolite", not the question that decides the class — so every entry now carries a `neverAdministered` sentence instead, and a test requires one. Two heuristics narrow where to look hardest, both learned the hard way: **an active metabolite is a candidate for administration and an inactive one is not** (every wrong entry was active), and **a metabolite of a designer drug is itself a plausible designer product** — the research-chemical market sells active benzodiazepine metabolites in their own right, which is how 3-hydroxyphenazepam got in. Nothing in the repo can check the pharmacology; what it can do is force the claim into view where a reviewer will read it. `tests/substance-class-seed.test.ts` also pins the nine known near-misses as administered, each assertion first checking the CID is really in the catalog since "not classified" passes vacuously for a typo. The queue also returns a `suppressed` count per reason — the original bug survived because nothing could say *why* a parameter kept coming back, and an invisible suppression layer is the same failure mirrored. `buildParameterGapsSql` is exported and the integration test executes THAT text (same anti-drift rule as `UNREVIEWED_REFERENCES_SQL`); the parameter lists are inlined from the TS registry so the SQL cannot drift from `parameterAppliesToSubstanceClass`. **The queue has two lanes, because "already filled" has two answers.** `CORE_COVERAGE_PARAMETERS` are MEASURED: they publish a pooled aggregate, so a missing `drug_parameters` row is the gap. `MODEL_DECLARATION_PARAMETERS` (the CV-1b axes `dispositionModel`/`eliminationModel`/`absorptionModel`, plus route-scoped `ka`) are DECLARED, and all four are `summarizable: false` — `recomputeAndCacheParameterSummary` returns before writing anything, so that row never appears however many cited entries exist. Ranking them into the core set would therefore have rebuilt the benzoylecgonine loop on purpose: a pair that can never satisfy the fill test, re-served every cycle forever. The declaration lane reads `parameter_entries` instead — `alreadyFilledSql` dispatches on the `fill_kind` discriminator the candidate CTE carries, and every returned row echoes `fill_kind` so the routine sends a categorical (or route-scoped numeric) payload rather than a numeric one; sending the wrong shape is refused by the endpoint and costs the cycle. Route is deliberately NOT part of that test: the queue is keyed (drug, parameter), one cited route retires the pair, and widening to every route is flag and tier-C work like deepening a thin value. Declarations rank behind the WHOLE core set for a drug — every model family needs the measured numbers too, so a compartment count is not worth more than a missing half-life — which means the unfocused queue rarely reaches them and a `methods` focus carrying the four ids is the intended route (see Agent focus config). `absorptionModel` carries `requiresAdministration` alongside `bioavailability`/`ka`, since "how does a dose of this enter the body" has no referent for a substance nobody doses; its two siblings deliberately do not, because a metabolite still distributes and is still cleared. Two invariants are easy to half-implement here and both are enforced structurally. **Both permanent layers bind every write path, not the one you thought of**: `upsertDrugParameter` is the choke point **most** writers funnel through (parameter PUT, `applyApprovedEditEffects`, `recomputeAndCacheParameterSummary`), so the guard lives *there* — but it is not every writer, and treating it as one is how two boundaries were missed: `applyApprovedParameterEntry` writes a `parameter_entries` row directly, and `researchImportStore` writes **both** tables directly with its own upsert. Each carries its own check (`assertEntryParameterApplicable`, and a `blockedParametersFor` preflight that skips-and-reports rather than aborting a whole import over one impossible parameter). Before adding a writer here, grep for `insert(drugParameters)` and `insert(parameterEntries)` rather than trusting the choke point — `parameterWriteBlockedBy` resolves marker **and** substance class in one join and `upsertDrugParameter` throws `ParameterNotApplicableError`; the callers pre-check only to give a specific 409 (`parameter_not_applicable`). Enforcing the marker alone would have made the class rule a queue-display convention rather than a fact about the data — a metabolite could still be handed a bioavailability, and the queue would call the pair impossible while the monograph served a number for it. The **absent cooldown is deliberately not a write barrier**: it records that a search came back empty, not that the quantity cannot exist, so someone who has now found a source must be able to store it — that is the outcome the cooldown is waiting for. Symmetrically, `PATCH /api/drugs` 409s (`substance_class_conflict`, listing the offending parameters) rather than reclassifying a substance whose administration-requiring parameters still hold values or entries; a change *to* `drug` is never blocked, since widening what is defined creates no contradiction and is the escape hatch from a wrong classification. Guarding just the PUT left approval able to publish an edit queued before the marker landed, and an entry recompute able to cache an aggregate for it. The recompute *skips* rather than throws — one entry write cascades across every summarizable parameter on the drug, so a throw would let one marked parameter block its unmarked siblings — and clearing a value is always allowed, since removing the contradiction must not be blocked by the contradiction. The reverse direction is closed too: `PUT /api/drug-parameter-applicability` 409s (`parameter_has_value` / `parameter_has_entries`) rather than marking a pair that already serves a number, because deleting curated data as a side effect of a classification change is not a safe default. **Admin focus narrows inside the query, before `LIMIT`**: `resolveFocusNarrowing()` (exported from `api/agent-focus.ts`) resolves the config to `{parameters, drugIds}` and the lane inlines it as a WHERE fragment. Filtering the *returned page* instead would report "no work" whenever in-scope candidates rank below the global cut — a focus on `clearance`, last in the core priority order, goes silent the moment two higher-ranked drugs fill the 20 rows — so the prompt now tells the routine NOT to re-apply focus to this queue, and the response echoes `focus` so an empty narrow scope reads differently from an empty catalogue. In that type `null` means unrestricted and `[]` means **nothing is in scope** — a real answer, not a missing one. An admin who picked `mode = "parameters"` and selected none, or whose page focus resolves to no drug monographs, has scoped the parameter action to the empty set, and §3 says the routine logs `no_change` "rather than reaching outside the focus set"; collapsing `[]` to unrestricted would have the agent quietly work the whole catalogue against an explicit instruction. `= ANY(ARRAY[]::text[])` is false for every row, so the empty scope needs no special casing in SQL — only the resolver and `focusPredicates` must avoid treating empty as absent. `NO_NARROWING` is reserved for `mode='all'` and a genuinely missing config row. **Two more places the invariant leaks if you only guard the obvious one**: `api/wiki/pages.ts` inserts the page and revision *before* `applyInitialParameters`, on a path with no transaction, so a blocked parameter would 500 with the page committed and the retry colliding with its own slug — `blockedParametersFor` preflights the whole bag before either branch writes and 409s naming every offender. And every direction of the invariant is check-then-write, so a marker creation, a parameter write and a reclassification racing each other could each see no conflict and all commit. `withDrugApplicabilityLock(drugId, fn)` takes the **same** `pg_advisory_xact_lock(drugId)` the recompute already uses (one lock per drug, always acquired first, re-entrant within a transaction — a second lock id would have risked ABBA against recompute) and **opens a transaction when the caller has none**. That last part is the whole trick: the lock is transaction-scoped, so on the auto-commit client it is released the instant its own `SELECT` returns and serializes nothing — and the direct `/api/drug-parameter` write calls `buildParameterUpdate` *before* the route's only `runInPoolTransaction` block, so a design that merely required callers to be transactional would have left the busiest path racing. Serializing by construction inside `upsertDrugParameter` instead means every present and future caller is covered; `applyInitialParameters` wraps its loop in one transaction so a batch pays for one pool rather than one per parameter. The marker PUT and the `PATCH /api/drugs` class change run their check-and-write through the same helper. ## Data patterns

- **NumericRange**: `{ min?, max?, value?, unit?, qualifier?, note? }`. Used for all PK parameters. Null/empty fields omitted in `data/components.ts`.
- **Range helpers**: `rangeRepresentative()` returns value if set, otherwise midpoint of min/max. `formatRange()` prefers min–max display. `meanRange()` returns value or midpoint.
- **Unit conversions**: Pivot through canonical mass (ng/mL) and molecular weight. Handle blood/plasma via `bloodPlasmaRatio`. Keep molar vs mass unit kinds explicit.
- **Catalog freshness**: `data/components.ts` is a *seed source* and the offline fallback, not a live view of the DB. It only changes when someone edits it or runs `npm run catalog:export`; `npm run catalog:check` reports how far it has drifted (weekly in the `catalog-drift` workflow). Details in `docs/catalog-sync.md`.
- **Search**: Data loader builds `_searchKey` (lowercase name + nameEn + category joined by tabs) for each component at load time.
- **Typeahead search**: Simulator, wiki-editor, and command-palette lookups should use `GET /api/drugs?view=search&q=...` and only hydrate a full drug row after selection. Avoid calling `loadComponents()` on mount outside views that truly need the whole catalog.
- **Analytical methods**: Method data and method filters are gated to admins or members of the `rettstoks` user group. Do not ship method fallbacks in client bundles.
- **Receptor targets**: Canonical receptor/target rows live in `receptor_targets`; drug-specific affinity, potency, efficacy, Ki/IC50/EC50/Emax, selectivity, interaction role, and references live in `drug_receptor_targets`. The monograph sidebar renders these rows inside the pharmacodynamics box from the single-drug `/api/drugs?id=...` response; insert primary/most important target relationships first because the UI preserves stored relationship order.

## Internationalization (bilingual app text)

Every PR that adds or changes user-facing app text MUST ship matching English and Norwegian strings. This is a hard requirement: a PR that introduces a new label, button, heading, placeholder, tooltip, `aria-label`, validation message, toast, or empty-state copy in only one language is incomplete.

- **Stack**: `i18next` + `react-i18next`, configured in `src/i18n.ts`. Fallback language is Norwegian (`nb`); the user's choice is persisted in `localStorage["kinetix-lang"]`.
- **Strings live in** `src/locales/en.json` and `src/locales/nb.json`. Every key MUST exist in both files. Group related keys under nested namespaces (e.g. `nav.*`, `auth.*`, `search.*`); reuse an existing namespace before inventing a new one.
- **In React**: `const { t } = useTranslation(); t("namespace.key")`. Do NOT hardcode user-prose in JSX, in attribute values (`title`, `aria-label`, `placeholder`, `alt`), or in arguments passed to toast/notification helpers. Interpolate values via `t("key", { count, name })` rather than string-concatenating translated fragments — word order differs between languages.
- **API responses**: server-side strings that can reach the UI (validation messages, error bodies) should be stable codes/keys translated at the React boundary, not human prose hardcoded in `api/`. When you must add a new error string, add a key to both locale files in the same PR.
- **Bilingual data columns** follow the existing `name` (Norwegian, primary) + `nameEn` (English) convention — see `db/schema.ts` and `src/types/index.ts`. New bilingual data columns use the same `*En` suffix.

### Excluded from this requirement

User-generated content stays in whatever language the author wrote it. Do NOT add locale entries or auto-translate:

- Wiki page titles/body and revision history (`wikiPages`, `wikiPageRevisions`)
- Drug discussion comments (`drug-discussions`)
- User-authored simulator case names (`simulatorCases`)
- The user-supplied `name` / `nameEn` fields on a drug component itself

If you are unsure whether a string is "app chrome" (localize) or "user content" (leave alone), the test is: would two users in different languages expect to see different text here? If yes, it goes through `t()`.

### Seeded and imported content is authored content — write it in Norwegian

Content a seeder, importer or research agent writes into the database is stored once and rendered verbatim, so it can never be localized afterwards. It follows the same rule as human-authored content: **Norwegian bokmål**. That covers the prose fields (`drug_parameters.value.note`, `parameter_entries.comments`, `drug_elimination_routes.note` and `label`, `drug_receptor_targets.evidence_note`, `paper_reviews.review_markdown`, fact statements), the display names a seeder mints in a catalog it writes to (`bio_entities.name` — `nameEn` is the English alternate), the `edit_summary` a seeder stamps on the revision it creates, and any fixed label a seeder wraps around that prose. Identifiers stay identifiers: parameter ids, units, enum values, gene/enzyme symbols, source tags like `deep-research`, and citation metadata in the source's own language.

Norwegian means its letters too: **`æ`, `ø` and `å` are written as themselves**, never folded to `ae`/`oe`/`aa` or `a`/`o`/`a` (`ærlig`, not `aerlig`; `målt`, not `malt`; `også`, not `ogsaa`). Nothing in the stack asks for the fold — request bodies stream as UTF-8, the API stores text unmodified, and the SPA renders it verbatim; `æøå` are folded only when deriving slugs and lookup keys, which no reader sees as prose. A character that arrives mangled is a transport fault to fix at the transport (`agents/drug-db-maintainer.md` §0), not a spelling to change, and the same applies to scientific symbols (`µ`, `≤`, `–`, `β`). `npm run audit:norwegian` lists stored prose written without them; `--apply` restores the spellings that cannot be anything else and leaves the ambiguous ones (`malt`, `både`, `væske`) for a reader.

The prompts that produce this content carry the same rule and must keep it — `agents/deep-research-drug-seeding.md` (inside the `PROMPT START`/`PROMPT END` markers), `.claude/skills/kinetix/SKILL.md`, and the per-agent "Content language" sections in `agents/*.md`. Their worked examples are Norwegian on purpose: an English example outweighs an English-language rule.

## Deployment

Production deploys to Vercel run through the `deploy-production` GitHub Action
(`.github/workflows/deploy-production.yml`). It is **manual, human-only**:
triggered via `workflow_dispatch` and it always deploys the tip of `main`.

- Do NOT trigger, modify the trigger of, or auto-invoke this workflow from an
  agent/automation. Releasing to production is a human decision — leave the
  "Run workflow" button to a person.
- Agents may edit the deploy steps (e.g. fix a CLI flag) via a normal reviewed
  PR, but must never add an automatic trigger (push/schedule/PR) or run the
  deploy themselves.

### Project-link safety

Git auto-deploy is disabled (`vercel.json` → `git.deploymentEnabled: false`), so
every release is a `vercel` CLI invocation. The Vercel project that receives the
deploy is decided entirely by the resolved link in `.vercel/project.json`
(written by `vercel pull` in CI, or `vercel link` locally) — **not** by which repo
you are in. A checkout linked to the wrong project will silently publish Kinetix
there and hijack that project's production domain. This is not hypothetical: a
Kinetix CLI deploy once landed in the `ketai` project and took over `ketai.be`
until a later `ketai` git deploy reclaimed the alias.

- `scripts/assert-vercel-project.mjs` is the guard. It fails unless
  `.vercel/project.json` points at the Kinetix project/org. The
  `deploy-production` workflow runs it between `vercel pull` and `vercel build`,
  so a misconfigured `VERCEL_PROJECT_ID` secret can never ship.
- Never run a bare `vercel --prod` against this repo. Before any local `vercel`
  command run `npm run check:vercel-link`; if it fails, re-link with
  `rm -rf .vercel && vercel link` and pick the `kinetix` project.
- Full rationale and recovery runbook: `docs/ops/vercel-project-link.md`.

Each row in the `agents` table carries a `status` column that drives a small state machine. The enum and allowed transitions live in `src/lib/agentStatus.ts`; every transition runs through `transitionAgentStatus` in `api/_lib/agentHelpers.ts` so the side-effects (history row, user role sync) stay in lockstep.

```
            ┌──────────┐  suspend  ┌────────────┐
   create ─▶│  active  │──────────▶│  suspended │
            │          │◀──────────│            │
            └────┬─────┘ reactivate└──────┬─────┘
                 │                        │
                 │     deactivate         │
                 └────────────▶┌──────────┐
                               │deactivated│  (terminal)
                               └──────────┘
```

- `active` — backing user role is `contributor` (or higher if the operator elevated it). Listed in `/api/agents`.
- `suspended` — reversibly disabled. User demoted to `authenticated`; hidden from the public listing.
- `deactivated` — terminal soft-delete. Row retained so revisions / pending_edits keep their FK targets. No further transitions allowed.

Every transition appends a row to `agent_status_history` (actor + reason); the latest is denormalized onto `agents.status_changed_*` for fast list reads. Hook fire outcomes land in `agent_hook_runs` — see `api/_lib/agentHooks.ts`.

Hook delivery is opt-in per agent. `agents.hooks_enabled` defaults to `FALSE` so a freshly seeded agent is scheduled-only; `fireAgentHook` skips the outbound POST unless at least one active agent has the flag set. The `kinetix-agent` row is backfilled to `TRUE` by migration 0028 because it owns the comment-and-fact evaluator routine (`agents/comment-and-fact-evaluator.md`).

### Self-review (`agents.self_review_enabled`, migration 0095)

An agent does not review what it wrote: the verification queue filters out rows it authored, `POST /api/agent-verifications` rejects a verdict on its own submission (`agent_verification_self_not_allowed`), and the moderator path refuses a self-approval (`approval_self_not_allowed`; for humans that refusal is now the `review.edit.decideOwn` row of the capability matrix — see below). That is the default and it stays the default — two independent readers is what peer verification *is*. But the rule was unconditional, and a deployment running one specialised agent has no second reader, so everything that agent filed sat in the human queue indefinitely.

`self_review_enabled` is the per-agent escape hatch, flipped by an admin in **Admin → Agents** (a `Self-review` badge marks the row) and read back through `isSelfReviewAgentUser`. Turning it on for one agent changes three things **for that agent only**:

- **Queue** (`api/agent-verifications-queue.ts`) — the author-exclusion predicate is dropped (`notAuthoredByCaller` returns `undefined`) *and* the already-verified `NOT EXISTS` starts ignoring implicit rows. Both are required: every agent submission carries an implicit-approve row, so relaxing only the author filter leaves the feature inert with nothing to show for it.
- **Verdict** (`api/agent-verifications.ts`) — a verdict on its own target is accepted, but a self-**approval** requires a rationale of ≥20 chars (`agent_verification_self_approval_needs_rationale`): the whole justification for what the grant buys is that the verdict is a second, *reasoned* act, and the schema otherwise only demands prose for `dispute`/`abstain`. It upserts over the implicit-approve row on the same `(agent, target)` slot, so the agent's stake is counted once either way, and a later dispute is a correction rather than a second vote. `visibleVerificationTargetIds` takes the same `callerSelfReviews` exemption, since it runs first and would otherwise 404 the verdict before the handler's rule is ever consulted.
- **Moderation** (`api/pending-edits.ts`) — approve/return of its own pending edit is allowed, but only because `review.edit.decide` was already checked; on a contributor-tier agent the flag unlocks nothing here. Two carve-outs sit inside the exemption: a `clinical_case` is never self-approved by an agent (spec §12 Stage 12 — otherwise the moderator path becomes a way around the human-expert rule `applyOnAgentConsensus` already enforces), and an **open dispute blocks it** (a moderator may overrule an objection; the objected-to edit's own author may not — that one applies to humans too, see below).
- **Evidence level** (`src/lib/verificationLevel.ts`, `api/_lib/verification-levels.ts`) — the trusted agent's own re-verification counts as a second qualified verification, so a self-reviewed value reaches **level 2** instead of sitting at level 1 ("verified by its author only") forever. This is one identity counted twice, and it is sound for one reason: the two things counted are different *acts* — the submit-time stake and a later reasoned verdict with a rationale — which for a self-reviewer collapse onto a single `(agent, target)` row. `authorSelfVerifiedRevisionIds` therefore requires an **explicit** (`is_implicit = false`) `approve` from a **self-review-enabled** agent that is `active` **and whose backing user still holds contributor+** (the kill switch demotes the user without touching `agents.status`, so a status-only check would leave the bonus standing after the switch is pulled), whose user **authored that revision**: verifying a peer earns no bonus (the peer's stake is already its own row), and an agent nobody vouched for earns none at all.

The consensus tally is sized by the grant the *verdict was admitted under*, passed down from the POST handler rather than re-read at apply time — otherwise an admin revoking self-review between the two would shrink the quorum and thereby publish the author's just-recorded approval, inverting what revocation means.

Consensus treats a self-review author as **an extra verifier, not a lower bar**: `effectiveConsensusQuorum(n, { authorSelfReviews: true })` sizes the pool at `n` instead of `n - 1`, so with two active agents the quorum *rises* from 1 to the design target of 2. Only a single active agent can carry its own edit alone — the deployment the flag exists for — and that still logs as degraded. What the flag never touches: an agent cannot moderate a **human's** edit under it from `/review` (`agent_moderation_of_human_edit_not_allowed` is a separate, unconditional check), a `clinical_case` still needs a human expert, and one dispute still holds an edit for a person.

**A person's proposal publishes on agent consensus too** (`kinetix-consensus@v2` / `kinetix-consensus-apply@v3`), under exactly the bar an agent's does — the pool quorum, the high-risk flagship and design-target requirements, the source-quote gate, and every dispute hold. A person holds no seat in the agent pool, so every active agent is an eligible verifier (the quorum arithmetic of `authorSelfReviews: true`). What still needs a person is a `clinical_case`, a proposal with no recorded author (the `unattributed` rule), and anything a dispute holds. People are needed where the agents cannot settle something, not to countersign what they all verified.

### Deciding on your own proposal (`review.edit.decideOwn`)

The human counterpart to the switch above, and the same dead end: on a deployment where the admin is the only reviewer, their own proposals sit in the queue with nobody left to clear them. `review.edit.decideOwn` (capability matrix, default **`admin`**, floor `editor`) lifts the `approval_self_not_allowed` / `return_self_not_allowed` refusal in `PATCH /api/pending-edits` for the caller's own submission. It **stacks on** `review.edit.decide` rather than replacing it — the waiver is of "a second pair of eyes", not of being a reviewer — and `PendingEditCard` mirrors it exactly (`mayDecideThisEdit`), so the Approve/Return buttons appear on your own card in the same breath as the endpoint accepts them.

What does *not* move:

- **A revision and a decision are separate calls.** The submitter-update branch runs first and only knows how to move a row to `pending`/`draft`, so `status:'approved'`/`'returned'` sent *together with* a payload change used to answer 200 with the payload saved and the status untouched. That shape is now refused (`pending_edit_decision_with_payload_change`, 400): PATCH the payload, then decide on the revised row with the refreshed review token. `rejected` keeps both of its meanings — bare it is the withdraw, with a payload it is the submitter revision it always was.
- **Rejecting your own edit** was never the blocked act — `isOwnCancel` (`status: 'rejected'`, no payload change) is the submitter withdrawing a proposal, needs no review capability, and stays the only meaning of the button on your own card. The review-path Reject control keeps its `!isOwnEdit` guard so there is one button per meaning.
- **An open dispute** blocks the self-decision for everyone, admins included, with its own code `self_decision_blocked_by_dispute` (rendered as `review.errors.selfDecisionDisputed`) so the UI can say *resolve the dispute first* rather than the flat "not your edit" the grant just disproved. An admin may overrule an objection — but as a dispute resolution, which is recorded as such, not by approving the edit it was raised against. The card carries the controls for that act (`DisputePanel` in `PendingEditCard`, reading `GET /api/disputes?targetType=pending_edit&targetId=N` and writing `PATCH /api/disputes?id=N`): uphold, overrule, or withdraw your own. Before it existed the refusal was a dead end — `/api/disputes` had no browser caller at all, so the page told the moderator to resolve something it gave them no way to resolve, and the block itself could not be lifted: it counted **raw** agent dispute verdicts, which a resolution cannot close (`agent_verifications` is testimony, with no status column). It now counts `unresolvedDisputeVerdictCount` — verdicts with no moderator ruling from the same author recorded *after* the verdict — so ruling on the objection lifts the block, while an agent that disputes again re-opens it. **Which ruling matters**: `rejected` overrules the objection and frees the proposal, `upheld` sustains it and asks for a return, a rejection or a revision — so an upheld ruling keeps refusing the author's own *approval* (`self_approval_blocked_by_upheld_dispute`, `upheldDisputeStands`), while leaving return and withdraw open, and another moderator may still approve over it. It binds the payload, not the row: revising the proposal in response to the ruling clears it. The signal is `proposed_meta.revisedAt` — a server-managed marker the submitter-update branch stamps only when the PATCH actually changes the payload — **not** `submitted_at`, which a bare `{status:'pending'}` re-stamps (issue 592) without changing a byte, and would therefore let an author clear a ruling by resubmitting the content it was made against. Same principle as the conflict marker beside it: an edit must not become approvable without an actual revision. No marker = ruling stands. The card mirrors this off `pendingEdits[].disputeUpheld`. **Upholding also carries out the disposition it names**: for a `pending_edit` target the same PATCH returns the proposal to its author (`api/_lib/upheld-dispute-return.ts`), writing the objection's own `reason_md` — with its evidence, trimmed to the 2000-char return-note cap — into `rejection_comment`, and firing the same `edit_returned` agent hook a manual return fires. A dispute is already the note a reviewer would have retyped: ≥20 chars of substantive, sourced reasoning saying what is wrong and what to change. Without it the ruling was bookkeeping only, and a **human**-raised dispute never reached the submitting agent at all — its sweeps watch for dispute *verdicts* (`agents/drug-db-maintainer.md` §2.B, which survive a ruling) and for *returns* (§2.C), never for rulings — so it sat until a moderator remembered to return it by hand. The payload is untouched (so the ruling keeps standing until a real revision) and verifications are kept (no content changed). The return carries the manual path's moderation guards, because `dispute.resolve` is not one of them: it requires `review.edit.decide`, refuses the resolver's own submission without `review.edit.decideOwn` — the **human** grant, which excludes active agents exactly as the manual path does, so an agent self-returns only through its own `agents.self_review_enabled` row and never on a clinical case or a model-structure axis (`return_self_not_allowed`), refuses a model-structure axis without `edit.modelStructure.decide` (`isModelStructureEdit`, admin-tier by default), and refuses an active agent returning a **human** contributor's proposal outright (`agent_moderation_of_human_edit_not_allowed`) — an agent can hold the editor role, so without that an uphold was a side door to a transition `PATCH /api/pending-edits` refuses. A skipped return is reported back as `pendingEditReturned: false` with a reason and surfaced on the card, so a proposal nobody returned is not mistaken for one that went back. The note's marker carries `raised <timestamp>` so an author can date the objection against their own revision history — nothing establishes which version the objection's *prose* was written about, since `POST /api/disputes` records no target version (issue 1321). It also refuses a payload whose `proposed_meta.revisedAt` is newer than the objection's `created_at`: no version token reaches this endpoint (a dispute is resolved by id, from the admin queue as readily as from the card), so the timestamps are what establish that the objection is about the payload it would be returned under — a re-stated objection keeps its `created_at`, which makes the check conservative in the safe direction. The update takes the same optimistic lock a reviewer's own return takes (`pendingEditReviewerLock`, on the truncated `submitted_at`), not status alone: a submitter revision keeps the row `pending` while replacing the payload, so a status-only predicate would return the **corrected** proposal under an objection written against the version it replaced — the ruling binds the payload, not the row. Ruling and return commit as one pool transaction (`runInPoolTransaction`): the ruling closes the row that authorizes the return, so a failure between them would leave a resolved dispute over a still-pending edit no retry can finish — the next PATCH answers `disputes_not_found` on the row it just closed.
- **Agents** are excluded explicitly (`isActiveAgentUser`), not just by the `editor` clamp on agent tokens: self-review for agents stays `agents.self_review_enabled`, granted one agent at a time, and an admin lowering this row to `editor` must not hand it to all of them at once.
- **Approval stamps** (`api/approvals.ts`, `isSelfApproval`) are untouched and still refuse self-signature at every tier. A stamp asserts that *someone else* read the content, so there is no tier at which giving yourself one means anything.

The `clinical_case` carve-out is agent-only. Spec §12 Stage 12 asks for a human expert moderator, and an admin acting on the moderator path is one; `applyOnAgentConsensus` still refuses to publish a clinical case without one.

## Opening a pull request

**Open every pull request ready for review — never as a draft** (`gh pr create`
without `--draft`, or `draft: false` through the API). Opening for review is
what wakes everything the branch needs at once:

- **Review.** The Codex connector starts a review when a pull request is opened
  for review, and a fresh one on every later push (`synchronize`). No
  `@codex review` comment is needed.
- **The full CI suite.** `unit-tests` and `migrations` (where its `paths:`
  apply) run alongside the cheap path-filtered workflows (`kinetics-core`,
  `parity`, `scripts-typecheck`, `server-shared-esm`, `catalog-sync`,
  `prompt-registry-sync`) on every push.
- **The merge path.** `codex-gate` merges the pull request on its own once
  Codex has signed off on the current head and the checks are green. Do not
  merge it yourself; the gate does that.

**A pull request's definition of done is CI green on the current head**, a clean
Codex review on that head (or one whose only findings are P2/P3, each filed),
and no merge conflict. Drive it there; a red or pending suite is work, not
something to report and walk away from.

Because every push runs the expensive suites, run the local checks **before**
pushing rather than letting CI find what they would have. Every branch runs
`npm run typecheck`, `npm run lint` and `npx vitest run`.

**A branch in the `migrations` scope runs three more:**

```bash
npx tsc -p tsconfig.migrations.json                       # migration-path types
npm run test:integration                                  # PGlite chain replay
DATABASE_URL='' npx tsx scripts/apply-migrations-build.ts  # no-DB smoke
```

"In the `migrations` scope" means the branch touches any path in the `paths:`
list of `.github/workflows/migrations.yml`, which is wider than the workflow's
name suggests: `tests/integration/**`, `tests/governance/**`, `tests/support/**`,
`package.json`, `package-lock.json`, `vitest.config.ts`, `tsconfig.json`,
`vercel.json` and several API write paths (`api/_lib/db.ts`,
`api/_lib/pending-edits-helpers.ts`, `api/_lib/knowledge-governance/**`,
`api/drug-parameter.ts`, `api/parameter-entries.ts`) — not just `drizzle/**`.
Read the workflow for the authoritative list rather than trusting this summary;
it is the one kept in step with the guards.

**None of those three is reachable from the base checklist**, which is the whole
reason they are listed separately:

- `npm run typecheck` is `tsc --noEmit` against `tsconfig.json`, whose `include`
  is `["src", "data", "db", "api"]`. `scripts/` and `tests/` are outside it, so
  the runner that applies migrations to production is typechecked by nothing
  else — that is exactly the hole `tsconfig.migrations.json` was added to close,
  and Vitest transpiles those files without typechecking them.
- `npx vitest run` cannot reach the integration suite: `vitest.config.ts`
  excludes `tests/integration/**` and `tests/governance/**` outright, and they
  run only under `vitest.integration.config.ts`.

The two real-Postgres service-container steps (deadlock shape, import
contention) are CI-only — PGlite cannot discharge them — so only the
`migrations` run in CI covers those.

**Drafts.** The workflows still treat a draft specially, for a pull request a
human chooses to open as one: `unit-tests` and `migrations` are skipped while it
is a draft (`draft == false` gate), `codex-gate` ignores it, and a push to it
raises no review — comment `@codex review` to get one. Do not convert a pull
request to draft yourself, and do not open one as a draft.

**Success, not snapshot.** `codex-gate` requires a *successful* `unit-tests` run
on the head before it will merge (`REQUIRE_SUCCESS_RE`), which is deliberately
stricter than the rest of its check logic. The rest is a snapshot — it asks
what is failing or pending among the check runs that exist at that instant — so
a head whose suites have not registered yet, or that carries only a `skipped`
run left from a draft period, would otherwise read as green. Requiring a
success is what distinguishes "the suites passed" from "the suites have not
started". It fails closed: an event that queues no run holds the pull request
and says so in the gate's verdict.

## Reviewing a pull request

A PR merges through the `Codex gate` workflow (`.github/workflows/codex-gate.yml`), which reads the review back off the PR and merges once it finds a sign-off on the current head commit and the checks are green.

**When you finish a review and have nothing blocking, say so in a comment — do not sign off with only a 👍 reaction.** One line is enough ("No issues found."); the gate matches it against `CLEAN_RE`, which already covers the usual phrasings — *no issues / no concerns / didn't find / nothing to flag / LGTM / looks good*. Requesting changes or approving formally works too. All three are webhook-raising events.

The reason is cost, not preference. A reaction raises no webhook, so a gate run cannot be woken by one — it can only find a reaction by sitting in a poll loop and re-reading the PR, and that poll is billed wall-clock on a private repo. It was 74% of the gate's billed minutes over the active PR hours of 11 Aug. A comment arrives as an event the gate evaluates immediately, so the sign-off is *cheaper and faster* than the reaction: `WAIT_FOR_CODEX_MIN` is now 2 minutes, and a reaction that lands after it gives up waits for the next 2-hourly sweep instead of merging on the spot.

## Code review policy

Review findings are routed by severity. The full policy, including the
escalation rule, is in [docs/REVIEW_POLICY.md](docs/REVIEW_POLICY.md) and the operational
procedure is in [.claude/skills/steward/SKILL.md](.claude/skills/steward/SKILL.md).

In short:

- **P0 and P1 findings are fixed in the pull request that raised them**, before
  merge. A P0 takes priority over everything else on that pull request.
- **P2 and P3 findings are not fixed in that pull request.** Each one becomes a
  GitHub issue labelled `P2` and `review-debt`, linked back to
  the review comment. The issue must stay open until the PR that fixes it
  merges; `codex-gate` rejects a deferral linked to a closed issue. "The code is new in this PR" or "it is small" is not an
  exception. Once each is filed and its thread answered with the issue link,
  add the `findings-deferred` label; `codex-gate` then merges on that review
  instead of waiting for a clean one.
- **Any finding that touches the escalation areas listed in the policy is
  treated as at least P1**, whatever lower severity the reviewer assigned. The
  rule only raises severity: a P0 there stays a P0.

## Verification before pushing

- `npm run typecheck`
- `npm run lint`
- `npx vitest run`

A pull request is not ready while any of these is failing.
